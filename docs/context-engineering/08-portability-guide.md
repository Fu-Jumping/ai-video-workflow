# 08 可迁移性指南

本目录的规则与结构做了四类标注，目的是能从中提取一套供其他项目参考的**最小上下文工程骨架**，同时防止把项目特例误当通用经验。

## 1. 标注体系 `[通用规则]`

| 标注 | 含义 | 迁移性 |
| --- | --- | --- |
| `[通用规则]` | 与具体仓库无关的工作方法，任何项目可直接复用 | 直接迁移 |
| `[AVW 专用]` | 依赖 ai-video-workflow 的真实结构/契约（Step 0-7、镜头组、@三视图、verify 等） | 只迁移"有这一层"的思想，不迁移内容 |
| `[临时决策]` | 本轮为解决具体矛盾做出的选择，条件变化可复审 | 不迁移 |
| `[待确认]` | 勘察发现的不一致或未决问题 | 不迁移 |

## 2. 最小可迁移骨架 `[通用规则]`

给其他项目提取的六层结构（文件名可换，层次保留）：

```text
docs/context-engineering/
├── README.md                 # L0 索引：3 分钟上手路径 + 与权威规范的优先级声明
├── 00-project-context.md     # L1 身份/边界/事实源分层/生成产物/确认点
├── 01-context-loading-order.md  # L1 按任务类型的读取顺序
├── 02-workflow-map.md        # L2 流程全景 + 继承链 + 修改传播表
├── 03-step-contracts.md      # L2 每步：输入/产出/审核/回流/验证/失败模式/禁改项
├── 04-domain-glossary.md     # L3 领域术语（只收实际存在的概念）
├── 05-task-routing.md        # L2 任务 → 应读 → 可改 → 验证
├── 06-verification-gates.md  # L4 变更类型 × 验证矩阵 + 测试方法论
├── 07-decisions-and-open-questions.md  # L4 决策记录 + 缺口登记
├── 08-portability-guide.md   # L5 标注体系 + 迁移骨架（本文件）
├── 09-conversation-guidance.md  # L4 对话引导口径：首触引导/每轮状态脚注/载体登记
└── templates/                # L5 工作模板（简报/来源卡/审核记录/变更请求/测试报告）
```

配套的根级规则文件原则：

1. 根 `AGENTS.md` 只保留"所有 Agent 都必须知道"的稳定规则 + 上下文工程入口 + 停止确认点；不写大段业务介绍。
2. 每条重要规则可追溯到真实代码、测试、模板或历史决策；禁止臆造。
3. 单一权威出处：上下文工程文档做地图与路由，规范正文只有一份；冲突时声明优先级。
4. 每步契约至少回答：目标、上游输入、允许读取、产出、结构约束、审核点、回流方式、下游依赖、验证命令、常见失败与禁改项。
5. 验证矩阵按"变更类型"给最小验证与完整验证两档。
6. 缺口登记而非顺手修改：发现规则与实际不一致时记录 + 报告，不动业务行为。

## 3. 本项目中值得借鉴的具体做法 `[通用规则]`

1. **事实源分层**（母版源 / 项目源 / 运行镜像 / 观看层 / 执行面 / 宿主表面）：任何多表面项目都适用——明确"哪一层是真相、哪一层可重建"。
2. **机器✅/人工👤门槛归属标注**：把"工具能查的"和"必须人查的"显式分开，避免"验证通过=内容达标"的错觉。
3. **偏离登记制**（deviations.yaml）：例外必须显式登记且可见，禁止静默绕过校验。
4. **隔离端到端测试红线**：测试环境只见"链接 + 目录 + 构想"，比对只在事后由主环境做。
5. **修改传播表**：上游改动 → 影响范围 → 典型处理，写成表而不是散文。
6. **预期中间态说明**：分步校验中"刚完成上一步、下一步未建"的报错是正常的——把这类坑写进契约文档。

## 4. 不建议迁移的内容 `[AVW 专用]`

1. Step 0-7 的具体职责、三区块/五区块合同、镜头组/分镜/关键帧粒度、15 秒上限、"无配乐、无字幕"——这些是视频创作领域的契约，随 `packs/official-ai-video/` 走。
2. `@角色名三视图` / `@场景名场景图` 口径、SRC-xxxx 来源 ID 格式、Seedance/midjourney 平台参数门槛。
3. 具体命令名（verify/doctor/deviation/libtv…）、具体平台清单、具体目录名（`00_前期研究/` 等）。
4. 与 VitePress、pnpm workspace、`G:\develop-G\tests\` 约定绑定的操作细节。
5. 本项目的临时决策（D1-D5）与待确认事项（Q1-Q6）。

## 5. 迁移步骤建议 `[通用规则]`

1. 先勘察目标项目（结构、真实流程、规范来源、测试手段、生成产物），再写方案，最后落文件。
2. 按 §2 骨架建目录，但**逐文件判断**哪些层次在目标项目真实存在（没有的层不硬造，例如无多表面的项目不需要观看层术语）。
3. 为目标项目建立自己的标注体系，从第一天就区分通用/专用/临时/待确认。
4. 把根规则文件瘦身为入口，验证门禁对齐目标项目已有的真实命令。
5. 首轮交付时附验收清单与决策记录（参照 `implementation-plan-2026-08-23.md` §12 的形态）。

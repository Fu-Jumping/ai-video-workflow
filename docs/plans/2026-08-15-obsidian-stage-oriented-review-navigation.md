# Obsidian 阶段化审阅导航设计

**状态：已确认，待实施**
**日期：2026-08-15**
**适用范围：** `official-ai-video` 的 Obsidian 观看层（`export-obsidian` / `verify-obsidian`）

## 1. 背景与目标

现有 vault 根目录并列展示 `流程/`、`镜头/`、`镜头组/`、`画布/`、`数据表/`、`模板/`、`笔记/`。它们分别代表阶段产物、跨阶段镜头聚合、可视化、数据视图和用户内容，但目录名没有表达使用优先级，也没有反映实际审阅顺序。目录展开后，用户需要先回忆每个目录的职责，才能继续工作。

已确认的实际审阅路径是：

1. 按工作流阶段依次审核产物。
2. 进入同一阶段后，按镜头组和镜头顺序从头到尾审核。
3. 只有发现某一镜头跨 Step 3、Step 4、Step 5 不一致时，才需要把同一镜头的多个阶段内容放在一起联查。

本设计目标是让目录树直接表达这条路径：阶段审核是主入口，按镜头联查是辅助入口，数据和画布是工具，笔记是独立的人类内容区。

## 2. 设计决策

采用“阶段主导 + 镜头联查辅助”的结构，而不是仅给当前目录加序号，也不按镜头重排所有产物。

- `01_阶段审核/` 是唯一的主审阅树。阶段顺序和每个阶段内的镜头顺序都由路径和文件名固定表达。
- `02_按镜头联查/` 保留当前单镜头跨阶段页面和镜头组页面，但明确其只服务回溯、一致性核查和局部返修。
- 工具类产物不再与阶段产物、镜头对象和个人笔记处于同一根级别。
- Step Markdown 仍是项目事实源；Obsidian 仍是单向、可重建的观看层。该变更不得削弱 Step 3/4 帧级对齐、Step 4 文件合同、相对链接、增量导出或用户笔记保护。

## 4. 审阅行为

### 4.1 阶段审核

用户从 `00_开始审阅/00_项目首页.md` 进入，再按 `01_阶段审核/` 的阶段编号推进。

对于包含镜头级产物的 Step 3、Step 4、Step 5，阶段根目录新增生成的 `00_阶段审核.md`。它必须：

1. 标明当前审核阶段、上游前置条件和下游影响。
2. 列出本阶段镜头组，并在每个镜头组内按 `镜头 001`、`镜头 002` 等稳定顺序链接所有审核文件。
3. 给出本阶段的最小审核口径；Step 3/4 需明确帧级对齐，Step 4/5 需明确视觉继承与可执行性。
4. 提供上一阶段、下一阶段和 `02_按镜头联查/` 的短链接，不嵌入跨阶段完整内容。

阶段页是“开始一批审核”的导航页，不是新的工作流事实源，也不替代已投影的 Step 文件。

### 4.2 按镜头联查

`02_按镜头联查/单镜头/<shotId>.md` 延续当前单镜头沉浸式审阅页：可同时查看该镜头的 Step 3 分镜、Step 4 关键帧提示词、Step 5 视频提示词、参考素材、交接入口和审阅画布。

该页面不再被项目首页描述为常规批量审核路径，而是定位为：

- 某镜头在相邻阶段之间出现不一致时的回溯入口；
- 需要向智能体交接单镜头问题时的上下文入口；
- 对局部修改进行跨阶段复核的入口。

### 4.3 工具与笔记

`03_审阅工具/` 放置数据表、全局 Canvas、制作看板、智能体交接和模板。这些文件可被首页和阶段页链接，但不应与阶段源投影抢占主树。

`04_个人笔记/` 是唯一用户拥有的目录。增量导出、清理和强制重建必须继续保护用户在其中新增或修改的 Markdown；所有由单镜头页面创建的审阅笔记目标同步改为此目录。

## 5. 路径迁移映射

| 现有路径 | 目标路径 | 说明 |
| --- | --- | --- |
| `流程/步骤N - <名称>/...` | `01_阶段审核/0N_<名称>/...` | 主审阅路径，保留现有源文件、镜头组和镜头文件的排序逻辑。 |
| `镜头组/<groupId>.md` | `02_按镜头联查/镜头组/<groupId>.md` | 保留跨阶段镜头组聚合。 |
| `镜头/<shotId>.md` | `02_按镜头联查/单镜头/<shotId>.md` | 保留沉浸式跨阶段镜头页。 |
| `画布/镜头审阅/<shotId>.canvas` | `02_按镜头联查/逐镜头审阅画布/<shotId>.canvas` | 与单镜头页共同服务局部联查。 |
| `画布/*.canvas` | `03_审阅工具/全局画布/*.canvas` | 项目全局流程、流水线和审阅地图。 |
| `数据表/*.base` | `03_审阅工具/数据看板/*.base` | 只作为筛选、汇总和状态看板。 |
| `模板/*.md` | `03_审阅工具/协作模板/*.md` | 生成的协作模板，不与用户笔记混放。 |
| `03_制作看板.md` | `03_审阅工具/00_制作看板.md` | 制作准备工具。 |
| `04_智能体交接.md` | `03_审阅工具/01_智能体交接.md` | 局部问题定位后的辅助入口。 |
| `笔记/...` | `04_个人笔记/...` | 用户拥有内容；迁移策略必须避免覆盖。 |

`00_项目首页.md`、`01_审阅总览.md` 和说明页移动到 `00_开始审阅/`，以使根目录展开时先展示用户应从哪里开始，而不是展示工具类型。

## 6. 链接、增量导出与兼容性

导出器必须集中定义新路径，禁止在页面、Canvas、Base、UI 建议、验证器和测试中散落字符串常量。所有生成的 Markdown 链接、wiki link、Canvas file node、Base 嵌入、Bookmarks 和 Workspace 需要使用新的相对 vault 路径。

此次结构变化会让旧 manifest 中的生成文件变成 orphaned-generated。安全的默认增量导出不得静默删除旧路径，也不得删除用户内容。实现需采用明确迁移策略：

1. 检测旧布局的 manifest schema 或旧生成路径。
2. 在非 `--force` 导出中，对可确认未被用户改动的旧生成文件执行受控迁移或清理，并清晰报告操作；对被用户修改的旧生成文件保持 `skipped-user-modified`，不覆盖也不删除。
3. `--force` 继续只允许删除包含现有 manifest 且不含 `.git` 的观看层；重建后只产生新布局。
4. 用户笔记目录从 `笔记/` 迁移到 `04_个人笔记/` 时，不能依赖 `--force` 自动搬运用户文件。应在增量导出中做可恢复、可报告的迁移，或保留旧笔记目录并在新入口页显式链接，具体算法由实施计划定义并用测试覆盖。

这意味着 manifest schema 是否升版取决于迁移实现；不应为了目录改名而无理由改变项目事实源协议或写入本机绝对路径。

## 7. 验收标准

1. 新导出的 vault 根目录只出现设计中的五个主入口目录及系统 manifest，不再出现旧的 `流程/`、`镜头/`、`画布/`、`数据表/`、`模板/`、`笔记/` 根目录。
2. 默认项目首页能让用户进入阶段审核；Step 3、Step 4、Step 5 各有阶段审核入口，并按镜头组、镜头序号完整列出当前阶段产物。
3. 单镜头页、镜头组页和逐镜头 Canvas 可以继续做跨阶段联查，但不是项目首页的主审核路线。
4. Markdown、wiki link、Canvas、Base、UI 建议中的链接均为相对链接且可验证。
5. `verify-obsidian` 识别新路径和新的阶段审核页，同时继续校验源投影 hash、用户笔记目标、单镜头页、Canvas、Base、交接页和可选 UI。
6. 新旧布局的增量导出、`--force` 重建、用户笔记保留、用户修改生成文件的跳过行为都有自动化回归测试。
7. `pnpm build`、CLI 测试、官方示例外部 vault、项目内 vault 和可选 UI 示例全部通过；人工打开官方示例确认侧边目录能够一眼区分“阶段审核、镜头联查、审阅工具、个人笔记”。

## 8. 非目标

- 不重写 Step 文件目录、模板合同或工作流步骤。
- 不改变 Step 3 与 Step 4 的帧级映射规则。
- 不向 Obsidian 增加反向同步、自动调用智能体或新的第三方插件依赖。
- 不把 `02_按镜头联查/` 改成常规阶段审核的替代品。
- 不修改用户现有 `.obsidian/` 本地 UI 配置。
